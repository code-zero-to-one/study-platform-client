# 멘토링 도메인 화면 기획 문서

## 문서 목적

이 문서는 디자인 시안이 아니라 멘토링 도메인에서 아래 3개 화면이 어떤 역할을 가져야 하는지, 어떤 데이터를 읽고 어떤 행동을 허용해야 하는지 정의하는 기획/데이터 문서다.

- `나의 멘토링` (`/my-mentoring`, `/my-mentoring/[id]`)
- `쪽지상담` (`/note-consultation`)
- `멘토 운영 관리` (`/mentoring-management`, `/mentoring-management/requests`)

문서 기준은 2026년 3월 10일 현재 클라이언트 구현이며, 실제 서버 연동 상태와 어긋나는 지점은 별도로 기록한다.

---

## 1. 범위

### 포함 범위

- 화면 목적
- 대상 사용자
- 핵심 데이터 구조
- 상태값과 상태 전이
- 화면에서 가능한 주요 행동
- 라우트/진입 경로
- 화면별 책임 범위
- 현재 구현 제약과 향후 정리 포인트

### 제외 범위

- 비주얼 디자인
- 컴포넌트 스타일링
- 서버 API 명세 상세
- 결제사 연동 상세 플로우

## 2. 공통 도메인 모델

### 2.1 핵심 엔티티

#### `MentoringRequest`

멘티가 멘토에게 보낸 신청 단위다.

- 식별자: `id`
- 소유 멘토: `mentorId`
- 상담 방식: `method`
  - `note`
  - `simple`
  - `deep`
  - `offline`
- 결제 정보
  - `paymentMode`
  - `paymentMethod`
  - `paymentStatus`
  - `paymentMemo`
  - `paymentAmount`
- 신청자 정보
  - `menteeMemberId`
  - `menteeName`
  - `menteeRole`
- 신청 시각: `requestedAt`
- 희망 일정
  - `preferredDate`
  - `preferredTime`
- 신청 내용
  - `requestMessage`
  - `requestContents`
  - `attachedFileNames`
  - `referenceLinks`
- 처리 상태
  - `status`
  - `decisionNote`
  - `acceptedAt`
  - `rejectedAt`
- 연결 세션: `linkedSessionId`
- 대화 내역: `conversation[]`

#### `MentoringSession`

예약형 상담이 실제 일정으로 확정된 뒤 생성되는 세션 단위다. `note`는 세션을 만들지 않는다.

- 식별자: `id`
- 소속 멘토: `mentorId`
- 연결 신청: `requestId`
- 멘티 이름: `menteeName`
- 상담 방식: `method`
- 시작/종료: `startsAt`, `endsAt`
- 진행 안내: `placeNote`
- 세션 상태: `status`
  - `SCHEDULED`
  - `CANCELLED`
  - `COMPLETED`
- 예외 처리: `issueType`
  - `NONE`
  - `MENTOR_CANCELLED`
  - `MENTEE_CANCELLED`
  - `MENTOR_NO_SHOW`
  - `MENTEE_NO_SHOW`
- 운영 메모: `operationNote`
- 환불 상태: `refundStatus`
  - `NOT_APPLICABLE`
  - `PENDING`
  - `COMPLETED`
  - `NOT_ELIGIBLE`
- 환불 메모: `refundNote`
- 생성/수정 시각: `createdAt`, `updatedAt`

#### `MentoringReview`

멘티가 남긴 후기 단위다.

- 식별자: `id`
- 소속 멘토: `mentorId`
- 연결 신청: `requestId`
- 연결 세션: `sessionId`
- 작성자: `menteeMemberId`, `menteeName`
- 상담 방식: `method`
- 후기 값
  - `rating`
  - `recommendation`
  - `content`
- 생성/수정 시각: `createdAt`, `updatedAt`

#### `MentoringConversationMessage`

신청 이후의 타임라인 메시지다.

- 식별자: `id`
- 발신자: `sender`
  - `MENTEE`
  - `MENTOR`
  - `SYSTEM`
- 본문: `content`
- 생성 시각: `createdAt`

### 2.2 엔티티 관계

- `MentoringRequest 1개`는 `MentoringSession 0개 또는 1개`를 가진다.
- `MentoringRequest 1개`는 `MentoringReview 0개 또는 1개`를 가진다.
- `MentoringRequest 1개`는 `MentoringConversationMessage 여러 개`를 가진다.
- `note` 방식은 세션 없이 `Request + Conversation`만으로 끝까지 진행된다.
- `simple`, `deep`, `offline`는 수락 시 세션이 생성되고 이후 일정 관리, 취소, 노쇼, 후기로 이어진다.

### 2.3 공통 상태 체계

#### 신청 상태

- `PENDING`: 멘토 미처리
- `ACCEPTED`: 멘토 수락 완료
- `REJECTED`: 멘토 거절 완료

#### 결제 상태

- `PENDING_TRANSFER`: 수동 입금 대기
- `NOT_REQUIRED`: 결제 없음
- `CONFIRMED`: 결제 확인 완료

#### 사용자 화면용 파생 상태

`나의 멘토링`은 아래 사용자 상태로 다시 묶는다.

- `REQUESTED`
  - 신청은 들어갔지만 멘토가 아직 처리하지 않음
- `PENDING`
  - 멘토가 수락했지만 일정이 아직 확정 전인 상태로 보려는 의도
  - 현재 구현상 세션이 없고 request가 accepted인 케이스에 해당
- `CONFIRMED`
  - 세션 확정
- `COMPLETED`
  - 세션 완료 또는 종료 시각 경과
- `NO_SHOW`
  - 멘토/멘티 노쇼
- `CANCELLED`
  - 확정 일정 취소
- `REJECTED`
  - 신청 거절

### 2.4 상담 방식별 지원 범위

| 방식 | 신청 | 수락 | 일정 생성 | 대화 | 후기 | 운영 예외 |
| --- | --- | --- | --- | --- | --- | --- |
| `note` | 가능 | 가능 | 없음 | 화면 내 지속 | 가능 | 거절, 입금대기, 첫답변대기 |
| `simple` | 가능 | 가능 | 필요 | 알림/운영기록 중심 | 가능 | 일정변경, 취소, 노쇼 |
| `deep` | 가능 | 가능 | 필요 | 알림/운영기록 중심 | 가능 | 일정변경, 취소, 노쇼 |
| `offline` | 가능 | 가능 | 필요 | 알림/운영기록 중심 | 가능 | 일정변경, 취소, 노쇼 |

## 3. 데이터 소스 원칙

### 3.1 실제 화면 기준 현재 소스

- 멘토 목록/멘토 상세/내 멘토 프로필
  - 서버 쿼리 우선
  - 실패 시 로컬 fallback 사용 가능
- 멘토링 신청/세션/후기/쪽지상담 대화
  - 현재 `useMentoringManagementStore`가 사실상 단일 소스
  - Zustand persist 기반
  - 브라우저 로컬 저장소에 저장됨

### 3.2 현재 구조의 중요한 제약

- 멘티가 한 브라우저에서 만든 신청이 다른 브라우저/다른 세션의 멘토에게 자동 공유되지 않는다.
- 즉, 신청/운영/대화 데이터는 현재 진짜 서버 공용 데이터가 아니다.
- 따라서 아래 기획 문서는 도메인 요구사항 정의로 쓰되, 실제 서비스 완성 기준에서는 서버 소스로 옮겨야 한다.

## 4. 화면 1: 나의 멘토링

### 4.1 페이지 목적

멘티가 자신이 신청한 멘토링과 후속 상태를 한곳에서 추적하는 허브다.

이 화면이 해결해야 하는 질문은 아래 4개다.

- 내가 신청한 건이 현재 어디까지 왔는가
- 다음에 내가 확인해야 할 것은 무엇인가
- 확정 일정과 진행 채널/장소는 무엇인가
- 취소, 노쇼, 환불, 후기 등 후속 행동은 어디서 처리하는가

### 4.2 대상 사용자

- 멘티
- 멘토이기도 하지만 지금은 “내가 신청한 쪽”을 확인하려는 사용자

### 4.3 진입 경로

- `/my-mentoring`
- `/my-mentoring/[id]`
- 완료 페이지 CTA
- 알림/쪽지상담/멘토 운영 관리의 빠른 이동

### 4.4 읽는 데이터

- 인증: `memberId`
- 멘토 프로필 맵
  - 서버 목록 쿼리
  - 로컬 생성 멘토 fallback
- 신청 목록: `requestsByMentor`
- 세션 목록: `sessionsByMentor`
- 후기 작성 가능성: `reviewsByMentor`

### 4.5 화면이 보여줘야 하는 핵심 정보

#### 목록 레벨

- 진행 중 건수
- 예정된 멘토링 건수
- 지난 내역 건수
- 쪽지상담 건수
- 즉시 확인이 필요한 attention 카드
- 각 신청 카드별
  - 멘토명
  - 상담 방식
  - 현재 상태
  - 신청일
  - 희망 일정 또는 확정 일정
  - 결제 상태
  - 운영 이슈/환불 상태
  - 다음 행동 링크

#### 상세 레벨

- 신청 내용
- 현재 진행 상태
- 확정 일정 또는 희망 일정
- 진행 채널/장소
- 결제 상태
- 운영 기록
- 환불 상태
- 지금 먼저 할 일
- 다음으로 확인할 것
- 주요 CTA

### 4.6 허용 행동

#### 공통

- 멘토링 상세 진입
- 멘토 목록으로 이동
- 쪽지상담으로 이동

#### 상태별 허용 행동

| 상태 | 사용자의 핵심 행동 |
| --- | --- |
| `REQUESTED` | 알림 확인, 멘토 프로필 재확인 |
| `PENDING` | 알림 확인, 멘토 프로필 재확인 |
| `CONFIRMED` | 일정/채널/장소 확인 |
| `COMPLETED` | 후기 작성, 같은 방식 재신청 |
| `NO_SHOW` | 환불 상태 확인 또는 재신청 |
| `CANCELLED` | 환불 상태 확인 또는 재신청 |
| `REJECTED` | 멘토 목록 재탐색 또는 재신청 |

### 4.7 이 화면이 직접 하지 않는 일

- 신청 수정
- 결제 재시도
- 일정 변경 직접 요청
- 취소 직접 처리

이 화면은 “확인과 다음 행동 진입” 허브여야지, 실제 운영 처리 화면이 되면 안 된다.

### 4.8 지원해야 하는 상태 분류

#### 메인 구역

- 진행 중
  - `REQUESTED`
  - `PENDING`
- 예정된 멘토링
  - `CONFIRMED`
- 지난 내역
  - `COMPLETED`
  - `NO_SHOW`
  - `CANCELLED`
  - `REJECTED`

#### 별도 요약

- `쪽지상담`은 예약형과 성격이 달라 별도 요약/진입 카드로 다루는 것이 맞다.

### 4.9 페이지 성공 기준

- 멘티가 5초 안에 “지금 확인할 건”을 찾을 수 있어야 한다.
- 건별 상세에 들어가면 현재 상태와 다음 행동이 한 번에 이해돼야 한다.
- 예약형과 비동기형(`note`)을 혼동하지 않아야 한다.

### 4.10 현재 구현 제약

- 신청/세션 데이터가 로컬 스토어 기반이라 진짜 멘토-멘티 간 공유 상태가 아니다.
- 알림함 이동은 되지만 알림과 신청 데이터가 같은 서버 소스를 쓰는 것은 아니다.
- 일부 상태 설명은 화면용 파생 상태와 도메인 원상태가 완전히 분리돼 있지 않다.

## 5. 화면 2: 쪽지상담

### 5.1 페이지 목적

`note` 방식 상담을 채팅형 타임라인으로 이어서 처리하는 화면이다.

이 페이지의 역할은 단순 메시지함이 아니다. 아래 3가지를 동시에 해결해야 한다.

- 신청 승인 전/후/첫 답변 전/후를 같은 화면에서 설명
- 누가 다음 차례인지 명확히 보여주기
- 신청 문서와 후속 질문을 한 흐름으로 묶기

### 5.2 대상 사용자

- 멘티: 내가 신청한 쪽지상담 확인
- 멘토: 내가 받은 쪽지상담 처리 및 답변

### 5.3 진입 경로

- `/note-consultation`
- `/note-consultation?channel=sent&requestId=...`
- `/note-consultation?channel=received&requestId=...`
- 결제 완료 페이지 CTA
- 나의 멘토링 요약 카드
- 멘토 운영관리/신청 관리

### 5.4 읽는 데이터

- 인증: `memberId`
- 멘토-회원 매핑: `mentorIdByMember`
- 멘토 디렉터리 로컬 정보
- 신청 목록: `requestsByMentor`
- 파생 목록
  - `sentItems`
  - `receivedItems`

### 5.5 화면이 보여줘야 하는 핵심 정보

#### 목록

- 채널
  - `sent`: 내가 보낸 상담
  - `received`: 내가 받은 상담
- 검색어
- 선택된 채널 내 상태 요약 배지
- 각 요청 카드
  - 상대 이름
  - 역할
  - 최근 메시지
  - 최근 시각
  - 상태 배지
  - 미확인 답변 수(멘티 관점)

#### 상세

- 신청 원문
- 첨부/참고 링크
- 실제 대화 타임라인
- 현재 단계 배지
- 지금 가능한 행동
- 입력 가능 여부
- 비활성 사유

### 5.6 지원 상태

`쪽지상담`은 아래 상태를 독립적으로 보여줘야 한다.

| 키 | 의미 |
| --- | --- |
| `mentor-confirmation` | 멘토 수락 전 |
| `payment-confirmation` | 입금 확인 전 |
| `first-reply` | 멘토 첫 답변 전 |
| `my-reply` | 내가 다음 메시지를 보낼 차례 |
| `counterpart-reply` | 상대 답변 대기 |
| `rejected` | 신청 거절 |

같은 request라도 `sent`와 `received` 채널에서 라벨은 달라진다.

- 멘티 `sent`
  - `멘토 확인 대기`
  - `입금 확인 대기`
  - `첫 답변 대기`
  - `추가 질문 가능`
  - `멘토 답변 대기`
  - `신청 거절`
- 멘토 `received`
  - `수락 필요`
  - `입금 확인 필요`
  - `첫 답변 필요`
  - `내 답변 필요`
  - `멘티 추가 질문 대기`
  - `신청 거절`

### 5.7 허용 행동

#### 멘티

- 보낸 상담 목록 확인
- 검색
- 특정 request 상세 열기
- 멘토 첫 답변 이후 후속 질문 보내기
- 거절/대기 상태 확인
- 알림함/멘토 목록으로 이동

#### 멘토

- 받은 상담 목록 확인
- 검색
- 특정 request 상세 열기
- 수락 전 신청 관리로 이동
- 입금 확인 전 신청 관리로 이동
- 첫 답변 보내기
- 후속 답변 보내기

### 5.8 메시지 입력 가능 조건

#### 멘티가 보낼 수 있는 경우

- request.status = `ACCEPTED`
- 멘토 첫 답변이 이미 존재

#### 멘토가 보낼 수 있는 경우

- request.status = `ACCEPTED`
- 수동결제라면 `paymentStatus = CONFIRMED`

### 5.9 이 화면이 직접 하지 않는 일

- request 수락/거절
- 입금 확인

이 둘은 멘토 운영 관리로 보내는 것이 맞다.

### 5.10 페이지 성공 기준

- 사용자가 현재 대화가 “대기 중인지 / 내가 답할 차례인지”를 즉시 이해해야 한다.
- 신청 원문과 후속 대화가 끊기지 않아야 한다.
- `note`가 예약형 상담처럼 보이면 실패다.

### 5.11 현재 구현 제약

- 메시지/신청 데이터가 로컬 스토어 기반이라 멀티 세션 간 실시간 공유가 안 된다.
- deep-link는 지원하지만, 공용 서버 상태가 아니므로 다른 기기에서 같은 request를 재현할 수 없다.
- 실제 읽음 처리, 알림 연동, 미확인 카운트 서버 계약은 없다.

## 6. 화면 3: 멘토 운영 관리

이 영역은 사실 2개 화면으로 나뉜다.

- 운영 허브: `/mentoring-management`
- 신청 처리 화면: `/mentoring-management/requests`

둘을 합쳐 하나의 운영 도메인으로 본다.

### 6.1 페이지 목적

멘토가 본인 프로필 기준으로 들어온 상담을 처리하고, 일정과 예외 케이스를 운영하는 백오피스다.

이 영역이 해결해야 하는 질문은 아래와 같다.

- 지금 가장 먼저 처리해야 하는 신청은 무엇인가
- 수동결제/쪽지상담/예약형 상담 중 어떤 건이 막혀 있는가
- 오늘 일정과 중복 일정은 무엇인가
- 취소, 노쇼, 환불 후속은 무엇이 남았는가

### 6.2 대상 사용자

- 멘토 프로필을 가진 사용자

### 6.3 진입 경로

- `/mentoring-management`
- `/mentoring-management/requests`
- `/mentoring-management/requests?id=...`
- 멘토 프로필/운영 안내/디스코드 링크

### 6.4 읽는 데이터

#### 프로필 계층

- `useMyMentorProfileQuery`
  - 서버의 내 멘토 설정 조회
  - 서버 멘토 상세 조회
  - 실패 시 로컬 fallback

#### 운영 데이터 계층

- `requestsByMentor[mentorId]`
- `sessionsByMentor[mentorId]`
- `reviewsByMentor[mentorId]`

### 6.5 허브(`/mentoring-management`)가 보여줘야 하는 정보

- 내 멘토 프로필 요약
- 빠른 이동
  - 나의 멘토링
  - 쪽지상담
  - 후기 관리
  - 신청 관리
- 운영 체크
- 디스코드 입장 링크
- 대시보드 수치
  - 처리 대기
  - 입금 확인
  - 확정 일정
  - 후속 처리
- 우선순위 큐
  - 24시간 넘긴 신청
  - 입금 확인 필요
  - 쪽지상담 첫 답변 필요
  - 오늘 일정
  - 환불/취소 후속
- 예외 상황 분해
  - 멘토 취소
  - 멘티 취소
  - 멘토 노쇼
  - 멘티 노쇼
  - 환불 대기
- 일정 관리
  - 월별 캘린더
  - 확정 일정 목록
  - 대기 신청 일정

### 6.6 신청 처리 화면(`/mentoring-management/requests`)이 보여줘야 하는 정보

- 신청 체크리스트
- 상담 방식별 처리 기준
- 신청 목록 또는 단건 상세
- 각 신청의
  - 상태
  - 결제 상태
  - 신청 시각
  - 희망 일정
  - 요청 내용
  - 결제 메모
  - 멘티 정보
  - 현재 필요한 처리

### 6.7 멘토가 할 수 있어야 하는 행동

#### 신청 레벨

- 신청 수락
- 신청 거절
- 수동 입금 확인
- note 첫 답변 또는 후속 답변 전송

#### 예약형 수락 시

- 일정 확정
  - `startsAt`
  - `endsAt`
  - `placeNote`
  - `mentorNote`

#### 일정 레벨

- 일정 변경
- 일정 취소
  - 멘토 취소
  - 멘티 취소
- 상담 완료 처리
- 멘토 노쇼 처리
- 멘티 노쇼 처리

### 6.8 행동별 선행 조건

| 행동 | 선행 조건 |
| --- | --- |
| 수락 | request가 `PENDING` |
| 수동입금 확인 | request가 `PENDING`이고 paymentStatus가 `PENDING_TRANSFER` |
| 예약형 수락 | 일정 정보 필수, 시간 범위 유효, 기존 세션과 충돌 없음 |
| note 첫 답변 | request가 `ACCEPTED`, 수동결제면 입금 확인 완료 |
| 일정 변경 | 대상 session 존재, 변경 시간 충돌 없음 |
| 일정 취소 | 대상 session 존재, 사유 2자 이상 |
| 완료/노쇼 처리 | session이 `SCHEDULED`, 시작 시각 이후 |

### 6.9 운영 예외 지원 범위

#### 지원하는 예외

- 멘토 취소
- 멘티 취소
- 멘토 노쇼
- 멘티 노쇼
- 환불 대기
- 환불 불가

#### 현재 계산 규칙

- 멘토 취소/멘토 노쇼
  - 전액 환불 대기
- 멘티 취소
  - 시작 120시간 전 이상: 전액 환불 대기
  - 시작 24시간 전 이상: 부분 환불 대기
  - 시작 24시간 내: 환불 불가
- 멘티 노쇼
  - 환불 불가

### 6.10 이 영역이 직접 하지 않는 일

- 실제 카드 결제 승인
- 실제 환불 집행
- 서버 푸시 알림 발송
- 회계/정산 처리

이 화면은 운영 상태를 결정하고 기록하는 화면이지, 외부 결제/정산 시스템 자체는 아니다.

### 6.11 페이지 성공 기준

- 멘토가 24시간 내 처리 대상과 오늘 일정, 예외 후속을 한 번에 식별할 수 있어야 한다.
- `note`와 예약형 상담의 처리 규칙이 혼동되지 않아야 한다.
- 수락/거절/입금 확인/일정 확정/취소/노쇼가 모두 한 도메인 안에서 설명돼야 한다.

### 6.12 현재 구현 제약

- 운영 데이터는 서버 기반이 아니라 로컬 스토어 기반이다.
- 신청/세션/후기 데이터는 멀티 기기/멀티 세션 공용 상태가 아니다.
- 디스코드 링크와 운영 문구는 존재하지만 실제 외부 채널 연동 상태는 없다.

## 8. 꼭 유지해야 할 기획 일관성

### 8.1 책임 분리

- `나의 멘토링`은 확인 중심
- `쪽지상담`은 대화 중심
- `멘토 운영 관리`는 처리 중심

세 화면이 같은 데이터를 보더라도 목적이 같아지면 안 된다.

### 8.2 note와 예약형 분리

- `note`는 세션 없는 비동기 상담이다.
- 예약형(`simple/deep/offline`)은 세션 기반이다.
- 같은 화면에 섞여 보일 수 있어도 상태 해석과 행동 허용은 분리되어야 한다.

### 8.3 상태와 행동의 일관성

- 상태만 보여주고 행동이 없으면 허브가 아니다.
- 행동만 있고 현재 상태 이유가 없으면 운영 화면이 아니다.
- 각 화면은 항상
  - 현재 상태
  - 상태 근거
  - 다음 행동
  이 세 가지를 같이 제공해야 한다.

### 8.4 알림 의존성

- 알림함은 보조 진입점이다.
- 본문 데이터의 출처가 알림이 되어선 안 된다.
- 각 화면은 자체적으로 상태를 설명할 수 있어야 한다.

## 9. 현재 구현 기준의 가장 큰 리스크

### 9.1 데이터 일관성 리스크

가장 큰 리스크는 디자인이 아니라 데이터 소스다.

- 멘티 신청
- 멘토 확인
- 쪽지 답변
- 일정 확정
- 취소/노쇼

이 전부가 현재는 로컬 스토어 기반이다. 따라서 실제 서비스 수준의 일관성은 아직 확보되지 않았다.

### 9.2 기획상 다음 우선순위

1. `MentoringRequest`, `MentoringSession`, `MentoringReview`, `Conversation`을 서버 단일 소스로 이동
2. 알림/결제/환불과 도메인 상태 변경 이벤트 연결
3. 화면 3개는 같은 서버 상태를 다른 책임으로만 보여주도록 정리

## 10. 결론

이 세 화면은 각각 별도 목적을 가져야 한다.

- `나의 멘토링`은 멘티의 상태 허브
- `쪽지상담`은 note 상담 타임라인
- `멘토 운영 관리`는 멘토의 운영 콘솔

지금 필요한 것은 디자인 보정 이전에 이 책임과 데이터 경계를 먼저 고정하는 일이다. 이 문서는 그 기준 문서다.
