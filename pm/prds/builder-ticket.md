# PRD: builder-ticket

## Executive Summary

빌더 티켓은 사용자가 조건(이벤트 참여·추천 등)으로 발급받아, **후속 코스 결제 시 쿠폰처럼 할인 또는 무료 입장**에 사용하는 프로모션 수단이다. 운영/마케팅 어드민이 캠페인 단위로 티켓을 발급하고, 학습자는 결제 단계에서 보유 티켓을 적용한다. 기존 Toss 결제 흐름을 재사용하며, 결제 금액 산정 직전에 티켓 할인이 반영된다. 목표는 후속 코스 **결제 전환율 향상**과 캠페인 효과의 측정 가능성 확보다.

## Problem Statement

신규·이탈 학습자의 후속 코스 결제 전환율이 낮다. 현재 플랫폼에는 가격 장벽을 낮출 프로모션 수단이 전혀 없어, 마케팅 캠페인을 붙일 도구 자체가 부재하다. 그 결과:

- 추천을 통해 유입된 신규 학습자가 첫 결제 앞에서 이탈한다.
- 운영팀이 "이번 달 추천 이벤트 참여자에게 50% 할인" 같은 캠페인을 집행할 수단이 없다.
- 어떤 채널·캠페인이 실제 결제로 이어졌는지 추적할 수 없어, 마케팅 예산 의사결정 근거가 없다.

## User Stories

### US-1. 신규 학습자 — 추천 후 결제 망설임 해소
추천을 받고 가입했으나 후속 코스 결제를 망설이는 학습자로서, 보유한 빌더 티켓을 결제 단계에서 적용해 할인된 금액으로 결제하고 싶다.

**Acceptance Criteria**
- 결제 페이지에서 "사용 가능한 빌더 티켓" 목록을 볼 수 있다.
- 티켓을 선택하면 최종 결제 금액이 즉시 재계산되어 표시된다.
- 만료/사용완료/대상 외 티켓은 적용 불가 사유와 함께 비활성 표시된다.
- 티켓 적용 후 기존 Toss 결제가 정상 완료되고, 해당 티켓은 `USED` 상태가 된다.

### US-2. 운영/마케팅 어드민 — 캠페인 단위 발급
캠페인을 운영하는 어드민으로서, 대상 사용자군에 빌더 티켓을 캠페인 식별자와 함께 발급해 프로모션을 집행하고 싶다.

**Acceptance Criteria**
- `ROLE_ADMIN`만 발급 화면에 접근할 수 있다.
- 발급 시 할인 유형(정액/정률/무료), 값, 유효기간, 대상 코스 범위, 캠페인명을 지정한다.
- 발급 결과(성공 건수·실패 사유)를 확인할 수 있다.
- 발급된 티켓은 캠페인별로 조회·집계된다.

### US-3. 기존 사용자 — 추천 보상으로 티켓 획득
추천 링크로 지인을 가입시킨 기존 사용자로서, 추천 성사 시 빌더 티켓을 자동으로 지급받고 보유 목록에서 확인하고 싶다.

**Acceptance Criteria**
- 피추천인 가입(또는 정의된 전환 시점)이 확정되면 추천인에게 티켓이 자동 발급된다.
- 마이페이지에서 보유 티켓(상태·유효기간·적용 대상)을 확인할 수 있다.

## Functional Requirements

1. **티켓 발급**: 캠페인 기반 일괄 발급(어드민), 추천 성사 시 규칙 기반 자동 발급.
2. **티켓 모델**: 할인 유형(`FIXED`/`PERCENT`/`FREE`), 할인 값, 상태(`ISSUED`/`USED`/`EXPIRED`), 유효기간, 적용 대상 코스 범위, 캠페인 식별자.
3. **보유 티켓 조회**: 사용자별 보유 티켓 목록 API + 마이페이지 UI.
4. **결제 적용**: 결제 페이지에서 적용 가능한 티켓 필터링 → 선택 → 금액 재계산 → Toss 결제 연동.
5. **사용 처리**: 결제 성공 시 티켓 `USED` 전이(멱등 보장), 결제 실패/취소 시 티켓 원복.
6. **결제 실패 시 재발송**: 티켓 적용 결제가 Toss에서 실패(네트워크 오류·한도 초과 등)했을 때, 티켓 상태를 `ISSUED`로 원복한 뒤 사용자에게 "결제 실패 — 티켓이 복구됐습니다" 알림을 발송한다. 동일 티켓으로 재시도 가능 횟수는 최대 3회로 제한한다.
7. **Toss 환불 정책 연동**: 결제 취소/환불 요청 시 Toss 환불 API를 호출하고, 환불 성공 후에만 티켓을 `ISSUED`로 원복한다(환불 실패 시 티켓 원복 금지). 부분 환불은 이번 범위 밖(전액 환불만).
8. **캠페인 집계(어드민)**: 캠페인별 발급 수·사용 수·전환율 조회.

## Non-Functional Requirements

- **정합성**: 티켓 사용은 결제 승인과 원자적으로 묶여야 하며, 중복 사용(이중 차감)이 발생하지 않아야 한다(멱등 키 기반).
- **보안**: 발급/집계 API는 `ROLE_ADMIN` 게이트. 티켓 사용 API는 본인 소유 티켓만 허용.
- **성능**: 보유 티켓 조회 및 결제 적용 재계산은 체감 지연 없이(기존 결제 페이지 staleTime 정책 내) 동작.
- **관측성**: 발급/사용/만료 이벤트를 추적 가능한 형태로 기록(캠페인 집계의 근거).

## Success Criteria

- 빌더 티켓 **발급→사용 전환율**을 캠페인별로 측정할 수 있다(측정 가능한 수치로 노출).
- 후속 코스 결제 중 **쿠폰 적용 결제 비율**을 산출할 수 있다.
- 캠페인 식별자 기준으로 발급/사용/전환을 분해·비교할 수 있다.
- 이중 차감/오적용 결제 건수 = 0.

## Constraints & Assumptions

- 스택: Next.js 15(App Router) / React 19 / TypeScript 5 / Tailwind 4.
- 결제는 **기존 Toss 연동을 재사용**하며, 티켓 할인은 결제 금액 산정 직전 단계에 삽입한다.
- 백엔드에 **신규 `/api/v1` 쿠폰(빌더 티켓) 엔드포인트**가 필요하다(발급/조회/적용/집계).
- 어드민 화면은 `ROLE_ADMIN` JWT 클레임으로 보호되는 `(admin)` 라우트 그룹에 둔다.
- 서버 상태는 TanStack Query, 폼은 React Hook Form + Zod 규약을 따른다.

## Out of Scope

- 포인트/적립금 시스템.
- 실물 상품 교환/배송.
- 쿠폰 중첩 적용(스태킹) 및 복합 할인 규칙.
- B2B 대량 발급/정산.
- 부분 환불(티켓 부분 복구).
- 결제 실패 재시도 3회 초과 후 자동 티켓 만료 처리(향후 고려).

## Dependencies

- **백엔드**: 빌더 티켓 도메인 엔드포인트(발급/조회/적용/집계) — 미존재, 신규 개발 필요(프론트는 확정 전까지 TODO 플레이스홀더).
- **결제**: 기존 Toss 결제 모듈 및 결제 페이지(`(service)/payment`).
- **인증/권한**: `ROLE_ADMIN` 미들웨어 게이트(`/admin/*`).
- **추천 시스템**: 추천 성사 전환 시점 정의(자동 발급 트리거의 선행 조건).
